# 06 · 前端配置驱动设计

> 目标：**80% 的标准列表页用配置描述，15% 的差异用插槽，5% 的复杂页面老实手写。**
> 状态：**已实现**（`components/Crud/` + `hooks/useCrud.ts`），用户管理、角色管理两个页面已按此落地。

---

## 一、为什么不能"全配置化"

配置驱动的核心矛盾是：**配置越通用，越像在写一门新语言；配置越专用，越不通用。**

所以只做一类页面的配置化：**「搜索 + 表格 + 分页 + 新增/编辑弹窗 + 删除」**。
这类页面在后台系统里占 80%，且形态高度一致。

### 三层策略

| 层 | 覆盖 | 实现方式 |
|---|---|---|
| **配置** | 标准 CRUD 列表页 | 一个 `CrudPage` 组件 + 一份 schema |
| **插槽** | 需要局部定制（自定义列、额外按钮、联动） | schema 里允许 `render` 函数 / 具名插槽 |
| **手写** | 仪表盘、监控、树形编辑器、分步表单 | 正常写 `.vue` |

🔴 **硬规则**：schema 里允许写函数，但**不允许**出现 `if (module === 'user')` 这种按模块分支的代码。
一旦出现，说明该页面应该逃逸到手写。

## 二、Schema 结构

```ts
// types/crud.ts
export interface CrudSchema<T = any> {
  /** 唯一标识，用于 keep-alive、错误定位 */
  key: string

  /** 数据源：四个方法，缺哪个就禁用对应能力 */
  api: {
    list: (params: any) => Promise<R<PageResult<T>>>
    detail?: (id: string | number) => Promise<R<T>>
    create?: (data: any) => Promise<R<unknown>>
    update?: (data: any) => Promise<R<unknown>>
    remove?: (ids: string) => Promise<R<unknown>>
  }

  /** 主键字段名 */
  rowKey: keyof T & string

  /** 权限前缀，自动拼出 :add / :edit / :remove / :export */
  permissionPrefix?: string

  search?: SearchField[]
  columns: Column<T>[]
  form?: FormField[]

  toolbar?: ToolbarAction[]
  rowActions?: RowAction<T>[]

  pagination?: { pageSize?: number; pageSizes?: number[] }
  dialog?: { width?: number; mode?: 'dialog' | 'drawer'; labelWidth?: string }

  /** 提交前改写数据，返回 false 阻止提交 */
  beforeSubmit?: (model: any, mode: 'create' | 'edit') => any | false
  /** 提交成功后 */
  afterSubmit?: (mode: 'create' | 'edit', refresh: () => void) => void
}
```

### 搜索项

```ts
export interface SearchField {
  prop: string
  label: string
  type: 'input' | 'select' | 'date' | 'daterange' | 'number'
  placeholder?: string
  /** 字典类型，自动请求 /system/dict/data/type/{dict} */
  dict?: string
  /** 静态选项，优先级高于 dict */
  options?: Option[]
  width?: number
}
```

### 表格列

```ts
export interface Column<T> {
  prop: keyof T & string
  label: string
  width?: number | string
  minWidth?: number | string
  align?: 'left' | 'center' | 'right'
  fixed?: 'left' | 'right'
  sortable?: boolean
  /** 用字典渲染标签：传 dictType */
  dict?: string
  /** 日期格式化，如 'YYYY-MM-DD HH:mm:ss' */
  dateFormat?: string
  /** 完全自定义渲染 */
  render?: (row: T, index: number) => VNode | string
  /** 是否可复制 */
  copyable?: boolean
  showOverflowTooltip?: boolean
}
```

### 表单字段

```ts
export interface FormField {
  prop: string
  label: string
  type: FieldType
  required?: boolean
  rules?: FormItemRule[]
  dict?: string
  options?: Option[]
  placeholder?: string
  /** 栅格宽度，24 为整行 */
  span?: number
  /** 只在新建时显示 / 只在编辑时显示 */
  only?: 'create' | 'edit'
  /** 动态显示 */
  visible?: (model: any) => boolean
  /** 动态禁用 */
  disabled?: (model: any, mode: 'create' | 'edit') => boolean
  /** 字段下方的说明文字 */
  tip?: string
  /** 该字段不进表单，但提交时需要（比如隐藏的 id） */
  hidden?: boolean
}
```

### 字段类型注册表

```ts
export type FieldType =
  | 'input' | 'textarea' | 'password' | 'number'
  | 'select' | 'radio' | 'checkbox' | 'switch'
  | 'date' | 'datetime' | 'daterange' | 'time'
  | 'tree-select' | 'cascader' | 'upload' | 'editor'
```

每种类型对应一个渲染组件，注册在 `components/Crud/fields/index.ts`：

```ts
export const fieldRenderers: Record<FieldType, Component> = {
  input: ElInput,
  textarea: ElInput,
  number: ElInputNumber,
  select: DictSelect,      // 内置字典加载
  radio: DictRadio,
  date: ElDatePicker,
  // ...
}
```

**扩展新类型**只需要往这个 map 里加一项，不用改 `CrudForm` 本身。

## 三、运行时封装：useCrud

```ts
export function useCrud<T>(schema: CrudSchema<T>) {
  const query = reactive({ pageNum: 1, pageSize: schema.pagination?.pageSize ?? 10 })
  const list = ref<T[]>([])
  const total = ref(0)
  const loading = ref(false)

  const dialog = reactive({
    visible: false,
    mode: 'create' as 'create' | 'edit',
    model: {} as any,
    title: ''
  })

  async function fetchList() { /* ... */ }
  function openCreate() { /* ... */ }
  function openEdit(row: T) { /* ... */ }
  async function submit() { /* ... */ }
  function openRemove(rows: T[]) { /* ... */ }

  return { query, list, total, loading, dialog, fetchList, openCreate, openEdit, submit, openRemove }
}
```

使用方（用户管理页）大致长这样：

```vue
<script setup lang="ts">
import { userSchema } from './schema'

const crud = useCrud(userSchema)
</script>

<template>
  <CrudPage :schema="userSchema" :crud="crud" />
</template>
```

**一个标准页面 = 一个 schema 文件 + 一行组件调用**，这就是配置驱动要达到的效果。

## 四、组件拆分

| 组件 | 职责 | 是否可替换 |
|---|---|---|
| `CrudPage` | 编排：搜索区 + 工具栏 + 表格 + 分页 + 弹窗 | 否 |
| `CrudSearch` | 根据 `search[]` 渲染查询表单 | 是 |
| `CrudTable` | 根据 `columns[]` 渲染表格，处理多选 | 是 |
| `CrudForm` | 根据 `form[]` 渲染表单，处理校验 | 是 |
| `DictSelect` / `DictTag` | 字典加载与渲染 | 是 |

## 五、权限集成

`schema.permissionPrefix = 'system:user'` 后：

| 元素 | 自动应用的权限 |
|---|---|
| 工具栏「新增」 | `system:user:add` |
| 行操作「编辑」 | `system:user:edit` |
| 行操作「删除」 | `system:user:remove` |
| 工具栏「导出」 | `system:user:export` |

无权限的按钮**不渲染**（不是 `disabled`，避免用户反复点）。

> 🔴 前端隐藏只是体验优化，后端每个接口仍必须有 `@PreAuthorize`。

## 六、后端需要配合的三件事

| 需要 | 现状 |
|---|---|
| 分页统一 `{ total, list }`、参数 `pageNum/pageSize` | ✅ M1 已完成（`PageQuery` / `PageResult`） |
| 字典接口 `/system/dict/data/type/{dictType}` | ⏳ M4 |
| 新增/修改后返回最新数据或 null | ✅ 返回 `R<Void>` 即可，前端刷新列表 |

**不做**：后端下发列定义（表头、宽度、校验规则）。第一阶段保持前端配置，
避免过早滑向低代码平台——那会让调试变成"在 JSON 和代码之间来回跳"。

## 七、哪些页面不要配置化

| 页面 | 原因 |
|---|---|
| 仪表盘 | 布局是图表，不是表格 |
| 服务监控 | 实时刷新 + ECharts |
| 菜单管理 | 树形表格 + 图标选择 + 复杂的父子校验 |
| 角色分配权限 | 穿梭/树勾选，交互非标准 |
| 个人中心 | 表单为主，无列表 |
| 导入流程 | 上传 → 预览 → 校验 → 确认，多步骤 |

菜单管理可以做成「配置驱动 + 行内插槽」的混合形态，但不建议一开始就硬套。

## 八、落地顺序（重要）

🔴 **不要先写通用组件再写页面。** 那样设计出来的 schema 一定缺东西。

正确顺序：

```
1. 手写「用户管理」页面（最典型的 CRUD）
2. 手写「角色管理」页面
3. 对比两个页面，找出 80% 的共同结构
4. 抽象出 schema 类型 + CrudPage
5. 用 schema 重写这两个页面，验证抽象是否成立
6. 用「部门管理」验证第三个场景（树形表格 —— 会暴露 schema 的短板）
7. 再推广到字典/参数/公告
```

第 6 步是关键：**如果树形表格套不进去，就承认它不属于配置驱动**，而不是把 schema 改成一个万能解释器。

## 九、反模式清单

| 反模式 | 后果 |
|---|---|
| schema 里写 `if (module === 'xxx')` | 配置退化成代码，比手写更难维护 |
| 为了一个页面加 5 个 schema 字段 | 抽象泄漏，说明该页面该逃逸 |
| 把所有页面都配置化 | 复杂页面变成"配置地狱" |
| 完全禁止写函数 | 80% 的场景能覆盖，剩下 20% 会逼着你 hack |
| 没有插槽机制 | 一个自定义列就得放弃整个组件 |

## 十、验收标准

M3-3 完成后，用户管理页面应当满足：

- [ ] 页面文件 < 30 行（schema 单独放 `schema.ts`）
- [ ] 新增一个字段只需要改 schema，不改组件
- [ ] 删除用户管理的 schema，剩下三个模块照常工作
- [ ] 无权限账号看到的按钮数量与后端权限一致
