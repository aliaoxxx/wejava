# 部署方案：WAR + Nginx

> 不采用容器化部署。后端打成 war 交给 Tomcat，前端静态资源交给 Nginx，两者共用同一路径前缀。

## 1. 路径规划

对外地址有两种形态，**推荐根路径**：用户看到的 URL 更短，且和常见的 SaaS 管理后台一致。

| 形态 | 前端访问地址 | 接口地址 | 后端构件 |
|---|---|---|---|
| **根路径（推荐）** | `https://host/` | `https://host/prod/api/**` | `prod#api.war` |
| 子路径 | `https://host/prod/` | `https://host/prod/api/**` | `prod#api.war` |
| 开发 | `http://localhost:3300/dev/` | `http://localhost:8000/dev/api/**` | `dev#api.war` |

**为什么接口还带着 `/prod/api`**

前端走根路径只需要改构建参数和 Nginx，**后端一点不用动**；而把接口也挪到 `/api`
意味着要改 WAR 文件名（`prod#api.war` → `api.war`）、重新部署、清掉旧 context，
风险大、收益只是 URL 好看。用户看不出这个前缀，所以保留。

**前缀是如何生效的**

- 前端：Vite `base` 在构建时决定。默认 `pnpm build` 是 `/prod/`，用
  `VITE_APP_BASE=/ pnpm build` 构建的产物资源路径是 `/assets/...`（根路径形态）。
  路由用 `createWebHistory(import.meta.env.BASE_URL)`，刷新深层链接不会 404。
- 接口：请求基址由 `.env.production` / `.env.development` 的 `VITE_APP_BASE_API` 决定，
  **两种前端形态都用同一个值 `/prod/api`**，不需要改。
- 后端上下文：**WAR 文件名决定 Tomcat 的 context path**，`#` 会被解析成 `/`。
  `prod#api.war` → `/prod/api`，`dev#api.war` → `/dev/api`。

## 2. 服务器目录

```
/opt/wejava/
├── app/
│   ├── prod#api.war          # 后端生产包
│   └── dev#api.war           # 后端开发包（可选）
├── frontend/
│   ├── prod/                 # 前端生产静态文件（dist 内容）
│   └── dev/
└── logs/
    └── wejava-backend.log
```

Tomcat 与 Nginx 使用系统安装版本，`webapps` 指向 `/opt/wejava/app`（或软链）。

## 3. 构建

### 后端

```bash
# 生产
mvn clean package -Pprod -DskipTests
# 产物：target/prod#api.war

# 开发
mvn clean package -Pdev -DskipTests
# 产物：target/dev#api.war
```

`-Pprod` 会通过资源过滤把 `spring.profiles.active` 写成 `prod`，
并设置 `finalName=prod#api`。

### 前端

```bash
pnpm install

# 根路径形态（推荐）：资源路径为 /assets/...，接口仍走 /prod/api
VITE_APP_BASE=/ pnpm build

# 子路径形态：base 为 /prod/
pnpm build

pnpm dev            # 开发服务器 http://localhost:3300/dev/
```

构建产物在 `dist/`。两种形态的差别只在于资源引用前缀，**部署目录相同**。

## 4. 部署后端

```bash
cp target/prod#api.war $CATALINA_HOME/webapps/prod#api.war

# 配置环境变量（写进 $CATALINA_BASE/bin/setenv.sh）
export DB_HOST=127.0.0.1
export DB_PORT=3306
export DB_NAME=wejava
export DB_USER=wejava
export DB_PASSWORD='******'
export REDIS_HOST=127.0.0.1
export REDIS_PORT=6379
export REDIS_PASSWORD='******'
export JWT_SECRET='至少 32 位的随机串，务必替换'
export LOG_PATH=/opt/wejava/logs
```

启动后访问 `http://127.0.0.1:8080/prod/api/ping` 应返回 `{"code":200,...}`。

> 数据库表结构由 Flyway 在应用启动时自动迁移，首次启动请确认 DB 账号有 DDL 权限。
> 迁移文件在 `WEB-INF/classes/db/migration`，校验不通过会直接启动失败（故意的）。

## 5. 部署前端

```bash
rm -rf /opt/wejava/frontend/prod/*
cp -r wejava-frontend/dist/* /opt/wejava/frontend/prod/
```

Nginx 的 `root` 要指向 `prod` 这一层（不是它的父目录），否则根路径形态下
`/assets/xxx.js` 会被解析成 `/opt/wejava/frontend/assets/xxx.js` 而 404。

## 6. Nginx 配置

根路径形态（生产实际使用的配置，含 HTTPS 时把 `listen 80` 换成证书配置）：

```nginx
server {
    listen 80;
    server_name admin.example.com;

    # ---------- 前端：根路径 ----------
    location / {
        root /opt/wejava/frontend/prod;
        try_files $uri $uri/ /index.html;
    }

    # 入口不缓存，保证发版后立刻生效
    location = /index.html {
        root /opt/wejava/frontend/prod;
        add_header Cache-Control "no-cache, no-store, must-revalidate";
    }

    # 旧的 /prod/ 地址 301 到根路径；/prod/api/ 前缀更长，接口不受影响
    location = /prod { return 301 /; }
    location /prod/  { return 301 /; }

    # ---------- SSE 通道：必须关闭缓冲 ----------
    location ~ ^/prod/api/(stream|ai)/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
    }

    # ---------- 业务接口 ----------
    location /prod/api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
        client_max_body_size 20m;
    }
}
```

如果坚持子路径形态，把 `location /` 换成 `location /prod/`（`alias` 或 `root` 二选一），
并去掉两条 301 即可，其余不变。

**注意四点**

1. `try_files` 必须回退到 `index.html`，否则刷新 `/system/user` 会 404。
2. `index.html` 必须禁用缓存，否则发版后用户拿到旧的资源清单。
3. `location /prod/api/` 的优先级高于 `location /`（前缀更长），接口不会误入 SPA 回退。
4. SSE 那段的正则 `location ~` 优先级最高，`stream` / `ai` 两类长连接必须单独配置，
   否则事件会被 Nginx 缓冲住不发。

## 7. 发版与回滚

```bash
# 发版
scp target/prod#api.war server:/opt/wejava/app/
ssh server 'systemctl restart tomcat'
ssh server 'rsync -a --delete dist/ /opt/wejava/frontend/prod/'

# 回滚：保留上一版 war 与 dist
cp /opt/wejava/app/prod#api.war.bak /opt/wejava/app/prod#api.war
systemctl restart tomcat
rsync -a /opt/wejava/frontend/prod.bak/ /opt/wejava/frontend/prod/
```

## 8. 健康检查

| 检查项 | 方式 |
|---|---|
| 后端存活 | `GET /prod/api/ping` |
| 数据库 | `GET /prod/api/ping/db`（需登录） |
| 前端 | `GET /` 返回 200（子路径形态则探 `/prod/`） |
| 端口暴露 | 生产只应开放 80/443；Tomcat 8080 绑 `127.0.0.1` |

配合监控系统定时探测即可。
