# 02 · 认证与权限设计

> 方案：**自建 JWT + Redis 会话白名单**（路线 A）
> 不引入 OAuth2 授权服务器，不使用 `spring-security-oauth2-*` 系列依赖。

---

## 一、设计目标与边界

### 要做

| 能力 | 实现方式 |
|---|---|
| 账号密码登录 | `AuthenticationManager` + `DaoAuthenticationProvider` + BCrypt |
| 图形验证码 | Redis 存答案，2 分钟有效 |
| 登录防爆破 | Redis 计数，5 次失败锁 15 分钟 |
| 无状态鉴权 | JWT 放 `Authorization: Bearer` |
| 即时撤销 | Redis 白名单（jti），登出/禁用/改密立刻失效 |
| 双 Token | access 30min + refresh 7d（rotation） |
| 多端登录控制 | 单点登录开关，新登录踢掉旧会话 |
| 接口鉴权 | `@PreAuthorize("@ps.has('system:user:add')")` |
| 数据权限 | MyBatis-Plus 拦截器按 `data_scope` 拼 SQL |
| 在线用户 | Redis ZSET 记录活跃会话 |

### 不做（明确排除）

- ❌ OAuth2 / OIDC 协议端点
- ❌ 第三方客户端接入
- ❌ SSO 单点登录（未来若需要，走迁移路径，见第九节）
- ❌ 手机号/邮箱验证码登录（可作为扩展，架构已预留）

## 二、Token 设计

### 2.1 结构

Header：

```json
{ "alg": "HS256", "typ": "JWT" }
```

Payload（**刻意保持精简**）：

```json
{
  "iss": "wejava-admin",
  "sub": "1",
  "uid": 1,
  "uname": "admin",
  "jti": "0f1c2d3e-4a5b-6c7d-8e9f-0123456789ab",
  "typ": "access",
  "iat": 1761537600,
  "exp": 1761539400
}
```

**为什么不在 Token 里放权限列表？**

1. 权限多时 Token 会到 1~2KB，每个请求都传，浪费带宽
2. 权限变更后 Token 里的旧权限依然有效，必须等过期
3. 我们**每个请求本来就要查 Redis 白名单**，顺手就能取到权限，没有额外开销

### 2.2 两个 Token

| 类型 | TTL | 存储 | 用途 |
|---|---|---|---|
| `access_token` | 30 分钟 | 只在客户端内存/localStorage | 调业务接口 |
| `refresh_token` | 7 天 | Redis 记录 `jti` 状态 | 换新的 access |

**Refresh Rotation**：每次刷新，旧 refresh 立即作废，发一对新的。
好处是被盗用的 refresh 只能用一次；代价是前端并发刷新会打架——必须做单例刷新队列（见前端文档）。

### 2.3 签名算法

- 默认 **HS256**，`secret` 至少 32 字节（256 bit），从环境变量注入
- 支持**双 key 过渡**：配置 `jwt.secret` 与 `jwt.secret-previous`，验签时依次尝试
- **只接受白名单算法**，解析时显式指定 `HS256`，禁止信任 Token 头部的 `alg`（防止 `alg:none` 与算法混淆攻击）

```yaml
jwt:
  issuer: wejava-admin
  secret: ${JWT_SECRET}              # 32 字节以上，禁止硬编码
  secret-previous: ${JWT_SECRET_OLD:}
  access-ttl: 30m
  refresh-ttl: 7d
  clock-skew: 60s                    # 多实例时钟容差
```

## 三、Redis Key 规范

统一前缀 `admin:`，**所有 key 必须设置 TTL**（除显式声明的持久 key）。

| Key | 类型 | 值 | TTL | 用途 |
|---|---|---|---|---|
| `admin:auth:token:{jti}` | String | `LoginUser` JSON | 30m | 会话白名单，**鉴权时校验** |
| `admin:auth:refresh:{jti}` | String | `{userId}` | 7d | refresh 是否仍有效 |
| `admin:auth:user:{userId}` | Set | `jti` 集合 | 随会话刷新 | 按用户批量踢下线 |
| `admin:auth:online` | ZSet | member=`jti`，score=最后活跃时间戳 | 无 | 在线用户列表 |
| `admin:auth:captcha:{uuid}` | String | 验证码答案 | 120s | 图形验证码 |
| `admin:auth:fail:{username}` | String | 失败次数 | 15m | 防爆破计数 |
| `admin:auth:lock:{username}` | String | `1` | 15m | 锁定标记 |
| `admin:cache:perms:{userId}` | Set | 权限字符串 | 30m | 权限缓存 |
| `admin:cache:dict:{dictType}` | String | 字典 JSON | 1h ± 随机 | 字典缓存 |
| `admin:cache:config:{key}` | String | 参数值 | 1h | 参数缓存 |
| `admin:lock:{biz}:{id}` | String | 持有者标识 | ≤30s | 分布式锁（Redisson 管理） |
| `admin:limit:{uri}:{ip}` | String | 计数 | 60s | 接口限流 |

**约定**：

- 序列化统一用 **JSON**（`GenericJackson2JsonRedisSerializer` 或 Jackson 3 等价实现），**禁用 JDK 序列化**
- key 不允许出现中文、空格
- 批量删除禁止用 `KEYS`，用 `SCAN` 或维护索引 Set

## 四、登录流程

### 4.1 时序

```
前端                          后端                          Redis / MySQL
 │                             │                                │
 │ ① GET /auth/captcha         │                                │
 ├────────────────────────────►│ 生成 uuid + 4位算术题           │
 │◄────────────────────────────┤ SET captcha:{uuid} 120s ──────►│
 │  {captchaKey, captchaImage} │                                │
 │                             │                                │
 │ ② POST /auth/login          │                                │
 │  {username,password,        │                                │
 │   captchaKey,captchaCode}   │                                │
 ├────────────────────────────►│                                │
 │                             │ 校验验证码（取完即删）───────────►│
 │                             │ 检查 lock:{username} ──────────►│
 │                             │                                │
 │                             │ AuthenticationManager          │
 │                             │   → UserDetailsService 查库 ───►│ MySQL
 │                             │   → BCrypt 校验                │
 │                             │                                │
 │                             │ 失败：INCR fail:{username} ────►│
 │                             │      记录 sys_login_log        │
 │                             │      返回 1001                 │
 │                             │                                │
 │                             │ 成功：DEL fail:{username}       │
 │                             │      构建 LoginUser             │
 │                             │      签发 access + refresh      │
 │                             │      SET token:{jti} 30m ──────►│
 │                             │      SET refresh:{jti} 7d ─────►│
 │                             │      SADD user:{uid} ──────────►│
 │                             │      ZADD online ──────────────►│
 │                             │      记录 sys_login_log        │
 │◄────────────────────────────┤ {accessToken,refreshToken,expiresIn}
 │                             │                                │
```

### 4.2 关键实现

```java
public LoginVO login(LoginDTO dto) {
    // 1. 验证码（先校验，后删除，防重放）
    captchaService.verify(dto.getCaptchaKey(), dto.getCaptchaCode());

    // 2. 锁定检查
    if (tokenStore.isLocked(dto.getUsername())) {
        throw new BizException(ErrorCode.ACCOUNT_LOCKED);
    }

    // 3. 认证
    Authentication auth;
    try {
        auth = authenticationManager.authenticate(
                new UsernamePasswordAuthenticationToken(dto.getUsername(), dto.getPassword()));
    } catch (BadCredentialsException e) {
        int failures = tokenStore.incrLoginFail(dto.getUsername());
        loginLogService.recordFailure(dto.getUsername(), "用户名或密码错误");
        throw new BizException(ErrorCode.BAD_CREDENTIALS);
    } catch (DisabledException e) {
        throw new BizException(ErrorCode.ACCOUNT_DISABLED);
    }

    tokenStore.clearLoginFail(dto.getUsername());

    LoginUser loginUser = (LoginUser) auth.getPrincipal();
    return tokenService.createSession(loginUser);
}
```

**`UserDetailsService` 实现要点**：

- 查用户时带上 `del_flag = 0`
- `enabled = status == 0`
- 一次性查出角色 `role_key` 集合和权限 `perms` 集合，避免 N+1
- 密码字段带 `{bcrypt}` 前缀，交给 `DelegatingPasswordEncoder` 解析
- 用户不存在时也要执行一次 BCrypt 校验（防用户名枚举的时序侧信道）

## 五、请求鉴权流程

### 5.1 时序

```
请求 ──► CorsFilter ──► JwtAuthFilter ──► AuthorizationFilter ──► Controller
                          │                      │
                          │ 解析 Bearer token     │ 校验 @PreAuthorize
                          │ 验签 + exp            │ 校验 URL 规则
                          │ 查 token:{jti}        │
                          │ 命中 → 构建 Auth      │
                          │ 未命中 → 不设置 Auth  │
                          ▼                      ▼
                     （不中断请求）          未认证 → 401
                                          无权限 → 403
```

### 5.2 JwtAuthFilter 实现要点

```java
@Component
@RequiredArgsConstructor
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtService jwtService;
    private final TokenStore tokenStore;

    @Override
    protected boolean shouldNotFilter(HttpServletRequest request) {
        return PUBLIC_PATHS.stream()
                .anyMatch(p -> new AntPathMatcher().match(p, request.getServletPath()));
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String header = req.getHeader(HttpHeaders.AUTHORIZATION);
        if (StringUtils.hasText(header) && header.startsWith("Bearer ")) {
            try {
                Claims claims = jwtService.parseAccess(header.substring(7));
                // ★ 白名单校验：Redis 没有 = 已登出/被踢/已过期
                LoginUser user = tokenStore.getSession(claims.getId());
                if (user != null) {
                    var auth = new UsernamePasswordAuthenticationToken(
                            user, null, user.getAuthorities());
                    auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));
                    SecurityContextHolder.getContext().setAuthentication(auth);
                    tokenStore.touch(claims.getId());   // 刷新在线时间
                }
            } catch (ExpiredJwtException e) {
                req.setAttribute(AUTH_ERROR, ErrorCode.TOKEN_EXPIRED);
            } catch (JwtException | IllegalArgumentException e) {
                req.setAttribute(AUTH_ERROR, ErrorCode.TOKEN_INVALID);
            }
        }
        try {
            chain.doFilter(req, res);
        } finally {
            SecurityContextHolder.clearContext();   // ★ 防线程池串号
        }
    }
}
```

**三个必须写对的细节**：

1. **失败时只清空上下文，不抛异常** —— 抛异常会绕过 `ExceptionTranslationFilter` 变成 500
2. **`finally` 里 `clearContext()`** —— Tomcat 线程复用，不清会串号
3. **区分"过期"与"无效"** —— 前端据此决定"静默刷新"还是"跳登录页"

### 5.3 认证失败响应

```java
@Component
public class RestAuthEntryPoint implements AuthenticationEntryPoint {
    @Override
    public void commence(HttpServletRequest req, HttpServletResponse res,
                         AuthenticationException ex) throws IOException {
        Object err = req.getAttribute(AUTH_ERROR);
        // 1005 过期 → 前端静默刷新；1006 失效/未登录 → 前端跳登录页
        R<?> body = (err instanceof ErrorCode code)
                ? R.fail(code)
                : R.fail(ErrorCode.NOT_LOGIN);
        writeJson(res, HttpStatus.UNAUTHORIZED, body);
    }
}
```

| 场景 | HTTP | code | 前端行为 |
|---|---|---|---|
| 未带 token | 401 | 1006 | 跳登录页 |
| token 过期 | 401 | 1005 | **静默刷新**，成功后重放请求 |
| token 无效/被踢 | 401 | 1006 | 清本地状态，跳登录页 |
| 已登录但无权限 | 403 | 403 | 提示"无访问权限"，**不跳转** |

> 403 跳登录页会造成死循环，这是最经典的前端 bug。

**错误码别名**：`ErrorCode.NOT_LOGIN`（未携带 token）与 `ErrorCode.TOKEN_INVALID`（签名错误、已撤销、被踢）
共用 `1006`，前端处理逻辑一致；`ErrorCode.TOKEN_EXPIRED` 单独用 `1005`，唯一触发"静默刷新"的分支。

## 六、权限模型（RBAC）

### 6.1 三层结构

```
用户 ──N:N── 角色 ──N:N── 菜单/权限
  │
  └── 部门（决定数据可见范围）
```

### 6.2 权限字符规范

格式：`模块:实体:动作`

| 动作 | 含义 |
|---|---|
| `list` | 查询列表 |
| `query` | 查询详情 |
| `add` | 新增 |
| `edit` | 修改 |
| `remove` | 删除 |
| `export` | 导出 |
| `import` | 导入 |
| `resetPwd` | 重置密码（特殊动作，驼峰） |

示例：`system:user:list`、`system:role:dataScope`、`monitor:online:forceLogout`

**规范**：

- 全部小写，仅 `resetPwd` 这类复合动作用驼峰（与 RuoYi 生态保持一致，便于对照）
- 一个接口**只对应一个权限字符**
- 按钮权限（`menu_type='F'`）与接口权限**一一对应**，在菜单管理里维护

### 6.3 鉴权注解

```java
@PreAuthorize("@ps.has('system:user:add')")
@PostMapping
public R<Void> add(@RequestBody @Valid SysUserDTO dto) { ... }
```

**为什么不用 `hasAuthority`？**

`hasAuthority('system:user:add')` 无法表达"超级管理员"。若给超管塞入全部权限字符，
新增菜单后必须重新登录才生效，且 Token/缓存体积不可控。

因此统一用自定义 `PermissionService`，支持通配符：

```java
@Component("ps")
public class PermissionService {

    public boolean has(String perm) {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        if (auth == null || !auth.isAuthenticated()) return false;

        Collection<? extends GrantedAuthority> authorities = auth.getAuthorities();
        for (GrantedAuthority ga : authorities) {
            String owned = ga.getAuthority();
            if ("*:*:*".equals(owned)) return true;          // 超管
            if (owned.equals(perm)) return true;
            if (matchWildcard(owned, perm)) return true;     // system:user:* 之类
        }
        return false;
    }
}
```

`matchWildcard` 规则：`*` 匹配单段，`**` 匹配多段。

### 6.4 超级管理员

- 判定条件：用户拥有 `role_key = 'admin'` 的角色
- 授予权限：`*:*:*`
- **不可被删除、不可被停用、不可被改角色**（接口层拦截）
- 超管在菜单树里看到全部菜单（不走 `sys_role_menu` 过滤）

```java
if (loginUser.isSuperAdmin()) {
    return menuMapper.selectAllEnabled();
}
```

## 七、数据权限

### 7.1 实现链路

```
Service 方法打 @DataScope
        │
        ▼
DataScopeAspect（AOP）
  1. 取当前 LoginUser
  2. 查用户所有角色的 data_scope，取最宽松
  3. 生成 SQL 片段，放入 ThreadLocal
        │
        ▼
DataScopeInnerInterceptor（MP 拦截器）
  在 beforeQuery 里用 JSqlParser 把片段 AND 到 WHERE
        │
        ▼
最终 SQL
```

### 7.2 注解

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface DataScope {
    /** 部门表别名，默认 d */
    String deptAlias() default "d";
    /** 用户表别名，默认 u */
    String userAlias() default "u";
    /** 是否允许为空（为空时不加条件），默认 false */
    boolean allowEmpty() default false;
}
```

### 7.3 生成规则

| data_scope | SQL 片段 |
|---|---|
| `1` 全部 | 空（不加条件） |
| `2` 自定义 | `{deptAlias}.dept_id IN (SELECT dept_id FROM sys_role_dept WHERE role_id IN (...))` |
| `3` 本部门 | `{deptAlias}.dept_id = {currentDeptId}` |
| `4` 本部门及以下 | `{deptAlias}.dept_id IN (SELECT dept_id FROM sys_dept WHERE dept_id = {currentDeptId} OR FIND_IN_SET({currentDeptId}, ancestors))` |
| `5` 仅本人 | `{userAlias}.user_id = {currentUserId}` |

**多角色合并**：`1` > `2` > `4` > `3` > `5`，任一角色是"全部"则不加条件。

**空值保护**：若用户没有任何角色 / 部门为空 / 自定义范围为空集合，必须生成
`AND 1 = 0`（查不到数据），**绝不能退化成"不加条件"**——这会造成越权。

### 7.4 手写 SQL 的处理

MP 拦截器只改它自己生成的 SQL。手写 XML 的查询必须显式调用：

```java
// Service 里
String fragment = DataScopeContextHolder.get().toSql();   // 已含 AND 前缀
List<OrderVO> list = orderMapper.selectPageWithScope(fragment);
```

```xml
<select id="selectPageWithScope" resultType="OrderVO">
    SELECT o.*, u.nickname
      FROM biz_order o
      LEFT JOIN sys_user u ON u.user_id = o.create_by
     WHERE o.del_flag = 0
     <if test="scope != null and scope != ''">
       ${scope}
     </if>
     ORDER BY o.create_time DESC
</select>
```

> 这里必须用 `${}`，但内容是**后端生成**的固定片段，不含任何用户输入，因此不存在注入风险。
> 需在代码评审中明确标注例外。

## 八、会话管理

### 8.1 登出

```
1. 从 Authentication 取 jti
2. DEL admin:auth:token:{jti}
3. DEL admin:auth:refresh:{refreshJti}
4. SREM admin:auth:user:{uid} {jti}
5. ZREM admin:auth:online {jti}
```

只清前端 localStorage 是不够的——Token 仍可用于攻击，直到过期。

### 8.2 强制下线（踢人）

| 场景 | 操作 |
|---|---|
| 管理员在"在线用户"踢人 | 删除该 jti 对应的全部 key |
| 禁用账号 | 删除 `user:{uid}` 集合内所有 jti |
| 修改密码 | 同上，且比对 `pwd_update_time` 兜底 |
| 删除账号 | 同上 |
| 单点登录开启时新登录 | 先踢旧会话再建新会话 |

```java
public void kickUser(Long userId) {
    Set<String> jtis = redis.opsForSet().members(USER_KEY + userId);
    if (jtis != null) {
        jtis.forEach(jti -> {
            redis.delete(TOKEN_KEY + jti);
            redis.delete(REFRESH_KEY + jti);
            redis.opsForZSet().remove(ONLINE_KEY, jti);
        });
        redis.delete(USER_KEY + userId);
    }
}
```

### 8.3 在线用户列表

```java
public PageResult<OnlineUserVO> online(Integer pageNum, Integer pageSize) {
    // ZSet 按最后活跃时间倒序，分页取
    Set<ZSetOperations.TypedTuple<String>> tuples = redis.opsForZSet()
            .reverseRangeWithScores(ONLINE_KEY, start, end);
    // 再按 jti 批量取 LoginUser，过滤掉已过期的
}
```

**跨实例**：`admin:auth:online` 是全局 ZSet，多实例部署天然共享。
若 Redis 数据丢失，用户会被强制重新登录——这是可接受的降级。

## 九、未来迁移到 OAuth2 的路径

当前 Token 已遵循标准 claim（`iss/sub/iat/exp/jti`），权限字符也已独立于框架。

迁移到 Resource Server 时只需三步：

1. 部署 Keycloak（或其它 IdP），把用户/角色同步过去
2. 删除 `JwtAuthFilter` 与 `TokenStore`，改为 `oauth2ResourceServer().jwt()`
3. 写一个 `JwtAuthenticationConverter`，把 `perms` claim 映射为 `GrantedAuthority`

**业务代码零改动**，因为 `@PreAuthorize("@ps.has(...)")` 只依赖 `Authentication`。

## 十、关键类职责

| 类 | 职责 | 注意事项 |
|---|---|---|
| `SecurityConfig` | 过滤器链、CORS、密码编码器、`AuthenticationManager` | 白名单显式列出，禁止 `anyRequest().permitAll()` |
| `JwtService` | 签发/解析/校验 | 绑定算法白名单，校验 `iss`、`exp`、`typ` |
| `JwtAuthFilter` | 解析 Bearer、查 Redis、填充上下文 | 失败不抛异常；`finally` 清上下文 |
| `TokenStore` | Redis 会话读写、踢人、在线列表 | 所有 key 带 TTL |
| `AuthService` | 登录、刷新、登出、获取当前用户 | 事务边界不要包住 Redis 调用 |
| `CaptchaService` | 生成/校验验证码 | 校验后立即删除，防重放 |
| `PermissionService` | `@ps.has()` 实现 | 支持 `*:*:*` 与通配符 |
| `DataScopeAspect` | 解析数据权限，写 ThreadLocal | `finally` 必须 remove |
| `DataScopeInnerInterceptor` | 改写 SQL | 只处理 SELECT；无 scope 时跳过 |
| `RestAuthEntryPoint` | 401 JSON | 区分过期/无效 |
| `RestAccessDeniedHandler` | 403 JSON | 不要返回堆栈 |

## 十一、安全要求（上线前逐条确认）

- [ ] JWT `secret` 从环境变量注入，长度 ≥ 32 字节，未提交到 Git
- [ ] 解析时**显式指定算法**，拒绝 `alg:none`
- [ ] 密码使用 `DelegatingPasswordEncoder`，库中存 `{bcrypt}$2a$...`
- [ ] 登录失败 5 次锁定 15 分钟，且**按用户名+IP 双维度计数**
- [ ] 验证码一次性使用，校验后立刻删除
- [ ] Token 只放在 `Authorization` 头，**不放 URL 参数**（会进 Nginx 日志）
- [ ] 登出、禁用、改密后旧 Token 立即失效（Redis 白名单已保证）
- [ ] 401/403 返回 JSON，不返回 HTML 登录页
- [ ] CORS 只放行配置的域名，禁止 `allowedOrigins("*")` 与 `allowCredentials(true)` 同时出现
- [ ] Swagger 在生产环境关闭
- [ ] 所有写接口都有 `@PreAuthorize`（CI 里用脚本扫描比对）

## 十二、测试要点

| 用例 | 预期 |
|---|---|
| 正确密码登录 | 返回双 Token，Redis 有会话 |
| 错误密码 5 次 | 第 6 次返回"账号锁定"，即使密码正确 |
| 验证码复用 | 第二次返回"验证码错误" |
| 登出后用旧 Token 请求 | 401 + code 1006 |
| 禁用用户后用旧 Token 请求 | 401 + code 1006 |
| 改密后用旧 Token 请求 | 401 + code 1006 |
| 无权限角色访问接口 | 403 + code 403 |
| 访问他人数据（改 id） | 403 或查不到（数据权限生效） |
| 超管访问任意接口 | 200 |
| access 过期、refresh 有效 | 401 + code 1005，前端刷新后成功 |
| refresh 被重复使用 | 第二次 401（rotation 生效） |
| 并发 10 个请求同时 401 | 只触发 1 次刷新 |
