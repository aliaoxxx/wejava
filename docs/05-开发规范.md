# 05 · 开发规范

> 定位：**只写"会分歧"的决策**。能用工具或代码挡住的，不写在这里。
> 格式化 → `mvn spotless:apply`；统一返回 → `R<T>`；分页 → `PageQuery` / `PageResult`。
> 违反标 🔴 的条款，代码评审必须打回。

---

## 一、分层与依赖

```
controller → service → mapper
                │
                └── converter（Entity ↔ DTO/VO）
```

| # | 规则 |
|---|---|
| 1.1 | 🔴 Controller **禁止**直接依赖 Mapper |
| 1.2 | 🔴 Entity **禁止**出现在 Controller 的入参或返回值里 |
| 1.3 | 🔴 Service 之间可以互调，但**禁止**循环依赖 |
| 1.4 | 事务只开在 Service 层，Controller 不开事务 |
| 1.5 | `common` 不依赖 `security`、`system`；`security` 只依赖 `common` |
| 1.6 | 🔴 **`security` 禁止 import 任何 `system.*`**：安全基础设施不认识业务 |

### 分层职责划分

| 包 | 装什么 | 判定 |
|---|---|---|
| `common` | 返回体、异常、工具、traceId、异步线程池 | 与业务无关 |
| `security` | JWT 编解码、过滤器、会话存储、权限匹配、验证码 | **不 import `system`** |
| `system` | 登录业务、用户/角色/菜单、登录日志 | 可以 import `security` |

典型误判：`LoginUserDetailsService` 需要查 `SysUserMapper`，看起来"属于安全"，
实际依赖业务表，**必须放在 `system`**。`AuthService` 依赖 `LoginForm`/`LoginVO`，同理。

自检（CI 可跑）：

```bash
cd wejava-backend
grep -rn "import com.wejava.system" src/main/java/com/wejava/security/ && echo "❌ 存在跨层依赖" || echo "✅ 无跨层依赖"
```

## 二、包结构与命名

```
com.wejava.system/
├── controller/   XxxController
├── service/      XxxService（接口）
├── service/impl/ XxxServiceImpl（实现）
├── mapper/       XxxMapper
├── converter/    XxxConverter
└── model/
    ├── entity/   SysUser                     表映射（== 表名去掉 sys_ 的驼峰）
    ├── query/    SysUserQuery                查询条件，继承 PageQuery
    ├── form/     SysUserCreateForm / SysUserUpdateForm
    └── vo/       SysUserVO                   输出视图
```

> 跨模块的基础设施（认证、JWT、权限）放在 `com.wejava.security`，不混进 `system`。

**模型按用途分目录，不按"DTO"这种笼统概念分：**

| 目录 | 装什么 | 特征 |
|---|---|---|
| `entity/` | 表映射 | 带 `@TableName`、继承 `BaseEntity` |
| `query/` | 查询条件 | 继承 `PageQuery`，只放筛选字段 + 分页 + 排序 |
| `form/` | 提交表单 | 带 `jakarta.validation` 注解；Create 与 Update 分开 |
| `vo/` | 输出视图 | 只放前端要的字段 |

🔴 一个请求/响应对象只能属于其中一类，禁止"一个 UserDTO 同时当入参和出参"。

### Service 接口与实现分离

🔴 `service/` 只放**接口**，实现放 `service/impl/`，命名固定为 `XxxService` / `XxxServiceImpl`。

```java
// service/LoginService.java
public interface LoginService {
    LoginVO login(LoginForm form, String ip, String userAgent);
}

// service/impl/LoginServiceImpl.java
@Service
@RequiredArgsConstructor
public class LoginServiceImpl implements LoginService { ... }
```

| # | 规则 |
|---|---|
| S-1 | 注入点一律使用**接口类型**，禁止注入 `XxxServiceImpl` |
| S-2 | 实现类只加 `@Service`，接口不加任何注解 |
| S-3 | 接口方法必须有 Javadoc，实现类方法可以没有 |
| S-4 | 一个接口一个实现；出现第二个实现时，用 `@Primary` 或 `@Qualifier` 明确选择 |

**两个例外**（不建接口）：

| 类 | 原因 |
|---|---|
| `LoginUserDetailsService` | 已经实现 Spring 的 `UserDetailsService` 接口，再包一层没有收益 |
| `CaptchaRenderer` | 无状态、无外部依赖的渲染组件，不会被 mock 或替换 |

🔴 **同一目录下会有多个模块的同类文件，文件名必须带业务前缀**：

| 目录 | 示例 |
|---|---|
| `model/entity/` | `SysUser` `SysRole` `SysMenu` `SysLoginLog` |
| `model/form/` | `SysUserCreateForm` `SysRoleUpdateForm` `LoginForm` |
| `vo/` | `SysUserVO` `LoginVO` |

禁止出现 `CreateForm`、`UpdateForm` 这种不带前缀的名字。

> 这个结构的代价：新增一个"用户"功能要同时动 5 个目录，模块边界变弱。
> 换来的收益：同类对象集中，便于统一约束（比如给所有 Form 加注解）和批量重构。
> 若未来要把某个模块拆成独立服务，需要跨目录挑文件——这是已知的取舍。

跨模块共用的对象（如登录会话）放在 `security/model/` 下，不放进业务模块。

| 后缀 | 用途 | 禁止 |
|---|---|---|
| `Form` | 入参 | 禁止出现在返回值 |
| `VO` | 出参 | 禁止携带 password 等敏感字段 |
| `Query` | 查询条件，继承 `PageQuery` | 禁止打 `@TableName` |
| `Entity` | 持久化映射 | 禁止直接返回给前端 |

方法命名：`list` / `getById` / `create` / `update` / `remove` / `page`。
禁止 `doXxx`、`handleXxx`、`processXxx` 这类看不出动作的名词。

## 二之二、文件粒度：一个文件只放一个类型

### 硬规则（可机械检查）

🔴 **一个 `.java` 文件只能有一个类型声明**（class / interface / enum / record），文件名与类型名一致。

推论：

| 情况 | 是否允许 |
|---|---|
| 一个文件两个顶层类 | ❌ 禁止 |
| 嵌套类 `static class Foo {}` | ❌ 禁止，单独建文件 |
| 嵌套 record `record Captcha(...) {}` | ❌ 禁止，单独建文件 |
| 局部类 / 匿名内部类 | ⚠️ 允许（是表达式不是声明），但优先用 lambda |
| Lombok/MapStruct 生成的 `Builder` 等 | ✅ 不算（不是源码） |

**为什么不能只靠编译器**：Java 只强制"一个 **public** 顶层类型"，一个文件里塞三个包级私有类是合法的。嵌套类型则完全不受限制。

**为什么禁止嵌套**：文件承载两个变化原因；IDE 的"跳转到文件"失效；Code Review 时容易被忽略。

自检（CI 可直接跑）：

```bash
cd wejava-backend/src/main/java
for f in $(find . -name "*.java"); do
  n=$(grep -cE "^\s*(public |private |protected |static |final |abstract )*(class|interface|enum|record) [A-Z]" "$f")
  [ "$n" -gt 1 ] && echo "违反：$f （$n 个类型）"
done
```

> 后续可接 Checkstyle 的 `OneTopLevelClass` 规则进 CI。

### 软判断：什么时候该新开一个类

硬规则管"一个文件一个类型"，但"要不要拆成两个类型"仍需判断：

| 该拆 | 不该拆 |
|---|---|
| 一个类承担两个**不同层**的职责（既是 `UserDetails` 又是 Redis 会话对象） | 一组同职责的常量/枚举 |
| 一个类有两个**不同方向**的变因（安全契约变了 vs 会话字段变了） | 工具类的多个纯函数 |

实证：`LoginUser` 同时实现 `UserDetails`（Security 契约）和充当 Redis 会话对象（存储契约），
已拆为 `LoginSession`（纯数据）+ `AuthUser`（principal 适配器）。

反例：把 `DateUtils` 的 20 个方法拆成 20 个文件，或 `ErrorCode` 的 31 个枚举值各建一个文件 ——
那是"同一职责的多个取值"，不适用本规则。

### 接口方法不能搬走，但它的逻辑必须搬走

`UserDetails.getAuthorities()` 是框架规定的接口方法，**必须留在 `AuthUser` 里**。
但方法体里的一切业务语义都应该搬出去，让实现类只剩一行委托：

```java
@Override
public Collection<? extends GrantedAuthority> getAuthorities() {
    return AuthorityResolver.resolve(session);
}
```

`AuthUser` 从此不知道 `SimpleGrantedAuthority`、不知道 `*:*:*`、不知道超管特例 ——
它只负责"我是谁"，不负责"我有什么权限"。

### 方法不拆文件，但可以搬家

文件粒度规则管的是**类型**，不是方法。一个类里有 20 个方法仍然是一个文件。

但**方法里混了两个不同层的逻辑**时，该把逻辑搬到另一个**类**里，而不是拆文件。判定标准：

| 信号 | 说明 |
|---|---|
| 这段逻辑在别处也要用 | 例如权限匹配，`AuthUser` 和 `PermissionService` 都要用 |
| 这段逻辑能不启动框架就单测 | 纯函数、无上下文依赖 |
| 同一语义被定义了两次 | 最危险的信号，改一处必漏另一处 |

**实证**：`*:*:*` 曾在 `AuthUser.ALL_PERMISSION` 和 `PermissionService.ALL_PERMISSION` 各定义一次，
匹配规则也分散在两个类里。现已收敛为 `PermissionMatcher`：
`resolve()` 推导持有权限、`matches()` 判断命中，`AuthUser` 与 `PermissionService` 都只做委托。

🔴 **同一语义的常量只能定义一次**。发现第二处定义时，先把常量收敛到唯一来源，再谈功能。

### 数据权限使用方法

在 Service 的**查询方法**上加注解即可，无需改 SQL：

```java
@DataScope(deptAlias = "u", userAlias = "u")
public PageResult<SysUserVO> page(SysUserQuery query) { ... }
```

| 规则 | 说明 |
|---|---|
| 只对 MP 生成的 SQL 生效 | 手写 XML 需自行拼条件 |
| 别名要对 | `deptAlias` / `userAlias` 必须与 SQL 里的表别名一致 |
| 未标注 = 不限制 | 忘标注就是越权，新增查询方法时要检查 |
| 解析失败会拒绝执行 | 宁可报错也不放行，安全边界不能"降级" |

### 已落地的拆分实例

| 原类 | 拆分后 | 依据 |
|---|---|---|
| `LoginUser` | `LoginSession`（数据）+ `AuthUser`（Security 适配器） | 两种契约 |
| `TokenStore` | `SessionStore`（会话/在线）+ `LoginAttemptStore`（防爆破） | 两套 Redis key，两种变化方向 |
| `AuthService` | `LoginService`（认证）+ `TokenService`（令牌生命周期） | 登录流程 vs token 生命周期 |
| `CaptchaService` | `CaptchaService`（生命周期/校验）+ `CaptchaRenderer`（绘图） | 业务规则 vs 渲染实现 |
| `LoginLogService` | `LoginLogService`（落库）+ `UserAgentUtils`（UA 解析） | IO vs 纯函数 |
| `AuthUser.getAuthorities()` | `AuthorityResolver`（会话 → GrantedAuthority） | 接口契约 vs 转换逻辑 |
| `PermissionMatcher` | `PermissionMatcher`（判断够不够）+ `AuthorityResolver`（有哪些） | 匹配 vs 推导 |

## 三、模型三层

| 层 | 类 | 特点 |
|---|---|---|
| 持久化 | `Xxx extends BaseEntity` | 带 `@TableName`、`@TableLogic`；字段与表一一对应 |
| 入参 | `XxxCreateDTO` / `XxxUpdateDTO` | 带 `jakarta.validation` 注解；**不包含** id（新建）或必含 id（修改） |
| 出参 | `XxxVO` | 只放前端需要的字段；**绝不**放密码、盐、内部标记 |

🔴 **禁止**把 Entity 直接当 DTO 或 VO 用。三个理由：泄露字段、绕过校验、序列化陷阱。

审计字段（`createBy/createTime/updateBy/updateTime`）由 `AuditMetaObjectHandler` 自动填充，
Service 里 **禁止**手写 `setCreateTime(LocalDateTime.now())`。

## 四、Converter

🔴 **禁止** `BeanUtils.copyProperties`（反射、字段漏拷不报错、改字段名静默失效）。

统一用 MapStruct：

```java
@Mapper(componentModel = "spring")
public interface SysUserConverter {
    SysUserVO toVO(SysUser entity);
    List<SysUserVO> toVOList(List<SysUser> entities);

    @Mapping(target = "userId", ignore = true)
    SysUser toEntity(SysUserCreateDTO dto);

    void update(SysUserUpdateDTO dto, @MappingTarget SysUser entity);
}
```

| # | 规则 |
|---|---|
| 4.1 | 一个模块一个 Converter，放在 `converter` 包 |
| 4.2 | 字段名不一致时**必须**显式写 `@Mapping`，不要靠"碰巧同名" |
| 4.3 | 修改场景用 `void update(dto, @MappingTarget entity)`，避免新建对象丢字段 |
| 4.4 | 枚举/日期等特殊转换写 `default` 方法或 `@Named` 方法，不要塞进 Service |

## 五、分页

```java
public class SysUserQuery extends PageQuery {
    private String username;
    private Integer status;
}
```

```java
@GetMapping("/list")
public R<PageResult<SysUserVO>> list(SysUserQuery query) {
    Page<SysUser> page = query.toPage();
    Page<SysUser> result = userService.page(query, page);
    return R.ok(PageResult.of(result));
}
```

| # | 规则 |
|---|---|
| 5.1 | 🔴 `pageSize` 上限 100（`PageQuery` 已强制），Service 不要再放宽 |
| 5.2 | 🔴 `orderBy` 必须是数据库列名且来自白名单，禁止把前端字符串直接拼进 SQL |
| 5.3 | 返回值统一 `{ total, list }`，不叫 `records` / `rows` / `items` |
| 5.4 | 导出类大查询用流式查询，禁止把全表读进内存 |

## 六、统一返回与错误码

```json
{ "code": 200, "msg": "操作成功", "data": {}, "traceId": "..." }
```

| # | 规则 |
|---|---|
| 6.1 | Controller 一律返回 `R<T>`，禁止返回裸对象或 `ResponseEntity<Map>` |
| 6.2 | 错误码只能用 `ErrorCode` 枚举，**禁止**写魔法数字 `R.fail(5001, "...")` |
| 6.3 | 新增错误码必须同步更新 `docs/03-接口设计.md` 的错误码表 |
| 6.4 | 链路 ID 走通用的 `X-Request-Id` 头：上游传入合法值（`^[A-Za-z0-9_-]{8,64}$`）会沿用，否则服务端重新生成；同一值同时写入响应头、`R.traceId` 和日志 MDC |

---

## 七、异常

| # | 规则 |
|---|---|
| 7.1 | 🔴 Service 只抛 `BizException`，禁止 `throw new RuntimeException("...")` |
| 7.2 | 🔴 禁止空 `catch`；要么处理，要么包装后重抛并保留 cause |
| 7.3 | 参数校验用 `@Valid` + 注解，不要在 Service 里手写一堆 `if (x == null) throw ...` |
| 7.4 | 第三方异常（如 SQLException）必须在边界处转换成 `BizException`，不能裸露到 Controller |

---

## 八、事务

| # | 规则 |
|---|---|
| 8.1 | 🔴 `@Transactional` 只加在 Service 的 **public** 方法上 |
| 8.2 | 🔴 禁止类内自调用事务方法（`this.xxx()` 不走代理，事务失效） |
| 8.3 | 查询方法加 `@Transactional(readOnly = true)` |
| 8.4 | 事务内禁止远程调用、发 MQ、导出文件、上传 OSS |
| 8.5 | 一次事务只做一件事；批量操作分批提交，避免长事务锁表 |

---

## 九、日志

| # | 规则 |
|---|---|
| 9.1 | 🔴 禁止 `System.out.println`，禁止 `e.printStackTrace()` |
| 9.2 | 🔴 禁止打印密码、token、完整实体；必要信息用占位符 |
| 9.3 | 异常日志必须带上下文：`log.error("创建用户失败 username={}", username, e)` |
| 9.4 | 业务异常用 `warn`，系统异常用 `error`，正常流程不打卡点日志 |
| 9.5 | 日志级别：生产 INFO，禁止在循环里打 DEBUG |

## 十、MyBatis-Plus 使用边界

| 场景 | 做法 |
|---|---|
| 单表 CRUD、条件查询、分页 | ✅ MP（`LambdaQueryWrapper` / `selectPage`） |
| 跨表关联、聚合统计、复杂报表 | ✅ 手写 XML（`src/main/resources/mapper/`） |
| 超过 3 个 Wrapper 串联 | ⚠️ 考虑抽成 Mapper 方法或写 XML |

| # | 规则 |
|---|---|
| 10.1 | 🔴 禁止 `wrapper.last("limit 1")` 这类拼 SQL 的写法 |
| 10.2 | 🔴 `selectOne` 可能返回多条时必须加 `orderBy` + `last("limit 1")` 或改用 `selectList` |
| 10.3 | 逻辑删除字段统一叫 `del_flag`，用 `@TableLogic` |
| 10.4 | 批量插入用 `saveBatch`，且 JDBC URL 带 `rewriteBatchedStatements=true` |

## 十一、XML 规范

```xml
<!-- src/main/resources/mapper/system/SysUserMapper.xml -->
<mapper namespace="com.wejava.system.user.mapper.SysUserMapper">
    <resultMap id="UserVOMap" type="com.wejava.system.user.vo.SysUserVO">
        <id property="userId" column="user_id"/>
        <result property="deptId" column="dept_id"/>
    </resultMap>
</mapper>
```

| # | 规则 |
|---|---|
| 11.1 | 🔴 禁止 `SELECT *`，必须显式列出字段 |
| 11.2 | 🔴 参数一律 `#{}`；`${}` 只允许用于**后端生成**的固定片段（如数据权限条件），且必须在注释里说明 |
| 11.3 | 多表关联查询必须写 `resultMap`，不要依赖 `autoMapping` 猜字段 |
| 11.4 | XML 文件放在 `resources/mapper/<模块>/`，文件路径与 Mapper 接口一致 |
| 11.5 | 动态条件用 `<if test="...">`，禁止在 Java 里拼 SQL 字符串 |

## 十二、新增接口 Checklist

复制到 PR 描述里逐条打勾：

```
[ ] 路径符合 /模块/实体/动作，全小写短横线
[ ] 有 @PreAuthorize("@ps.has('模块:实体:动作')")，且权限字符已加入菜单数据
[ ] 入参是 DTO 且有 @Valid
[ ] 出参是 VO，不含敏感字段
[ ] 返回 R<T>，分页用 PageResult
[ ] Service 方法有正确的事务注解
[ ] 异常只抛 BizException，错误码来自 ErrorCode
[ ] 日志不含敏感信息
[ ] 手写 SQL 显式列字段、用 #{}、有 resultMap
[ ] 已更新 docs/03-接口设计.md 的接口表
[ ] mvn spotless:apply && mvn test 通过
```
